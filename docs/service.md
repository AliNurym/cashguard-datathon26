# CashGuard: запуск сервиса

Сервис принимает видео кассы, ищет признаки нарушений кассовой дисциплины и отдаёт вердикт, таймкоды,
кадры-доказательства и ссылку на норматив. Все модели работают локально (RT-DETRv2, OWLv2, DINOv2, Qwen3-VL-4B — Apache-2.0),
облачные AI-сервисы не используются, после загрузки весов интернет не нужен.

Состав:

| Путь | Что это |
|---|---|
| `cashguard/pipeline.py` | `Analyzer.run/analyze(video_path)`: детекторы (RT-DETR 2.5 кадра/с, OWLv2 1 кадр/с) → кэш `data/cache/<job_id>.json` → `build_scene` → классификаторы сейфа (`sc.safe_prob`) и денег (`sc.money_fn`) → вопросы VLM для правил L и H (`data/vlm_cache/<job_id>.json`), все три шага необязательны → `rules.detect` → кадры-доказательства с рамками → описание и норма из `cashguard/registry.py` |
| `service/app.py` | FastAPI: API для жюри (`/api/v1/*`, ключ `X-API-Key`) и веб-интерфейс (`/`) |
| `service/jobs.py` | Хранилище задач (память + `data/service/jobs/*.json`) и диспетчер одного воркер-процесса |
| `service/worker.py` | Воркер-процесс: модели грузятся один раз при старте, задачи обрабатываются строго по очереди |
| `service/static/` | Веб-интерфейс (HTML/CSS/JS без сборки и внешних зависимостей; шрифт Open Sans локально) |

## 1. Установка

```bash
uv venv --python 3.12 .venv
uv pip install --python .venv/bin/python -r requirements-service.txt
```

Веса моделей (один раз, около 9 ГБ вместе с VLM, дальше сервис работает без сети):

```bash
.venv/bin/python scripts/download_models.py
```

Скрипт качает Qwen3-VL-4B, RT-DETRv2, OWLv2 и DINOv2 только в формате safetensors и докачивает с места обрыва.

Классификаторы состояний (логистическая регрессия поверх DINOv2-base, `cashguard/states.py`):

- `models/safe_clf.joblib` — «сейф открыт», ряд 2 кадра/с для правила B;
- `models/money_clf.joblib` — «деньги на столе», правила A и C зовут его только в моменты ухода и входа.

Если файла нет или модель не загрузилась, сервис работает без неё (в логе `... off`): правило B тогда молчит,
правила A и C работают только по OWLv2.

Локальная VLM Qwen3-VL-4B (`cashguard/vlm.py`, около 9 ГБ памяти) отвечает на вопросы по кропу в моменты событий:
экран ноутбука после ухода кассира (правило L) и дверь после того, как кассир вошла и села (правило H).
Обычно 0–3 вопроса на ролик по ~1 с, не больше 12. Не загрузилась — правила L и H молчат, остальное работает.

## 2. Запуск

Из корня репозитория, **одним процессом uvicorn** (без `--workers` и `--reload`: очередь и воркер живут в этом процессе):

```bash
CASHGUARD_API_KEY=<ключ> .venv/bin/uvicorn service.app:app --host 0.0.0.0 --port 8000
```

Ключ можно сгенерировать так: `openssl rand -hex 16`. Без `CASHGUARD_API_KEY` сервис не стартует.

После старта воркер 10–15 с грузит модели и прогревает их; задачи, пришедшие в это время, ждут в очереди.
Готовность: `GET /api/v1/health` → `"worker": "ready"`.

- Веб-интерфейс: `http://<хост>:8000/`
- API: `http://<хост>:8000/api/v1/...`, Swagger: `http://<хост>:8000/docs`

Публичный URL для жюри — через обратный прокси или туннель, например `cloudflared tunnel --url http://localhost:8000`.
Машина с сервисом должна работать всё время проверки.

### Переменные окружения

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `CASHGUARD_API_KEY` | — (обязательна) | Ключ для заголовка `X-API-Key` |
| `CASHGUARD_DATA_DIR` | `data/service` | Задачи, загруженные видео, лог `service.log` |
| `CASHGUARD_JOB_TIMEOUT` | `300` | Предел обработки одной задачи, с. Дольше — воркер перезапускается, задача `failed` |
| `CASHGUARD_MAX_UPLOAD_MB` | `200` | Максимальный размер видео |
| `CASHGUARD_KEEP_API_VIDEOS` | `0` | `1` — не удалять видео, загруженные через API, после обработки |
| `CASHGUARD_SAFE_CLF` | `1` | `0` — не запускать классификатор сейфа (правило B молчит) |
| `CASHGUARD_MONEY_CLF` | `1` | `0` — не запускать классификатор денег (A и C только по OWLv2) |
| `CASHGUARD_FPS` | `2.5` | Частота кадров RT-DETR (на обучающих роликах 2.5 и 5 дают одинаковый результат) |
| `CASHGUARD_OWL_FPS` | `1.0` | Частота кадров OWLv2; `0.5` — запас по времени (проверено только симуляцией) |
| `CASHGUARD_VLM` | `1` | `0` — не загружать VLM (правила L и H молчат, экономия ~9 ГБ памяти) |
| `HF_HUB_OFFLINE` | `1` (в воркере) | Модели только из локального кэша; `0` разрешает обращаться к huggingface.co |

## 3. API (ТЗ, раздел 10)

Все запросы к `/api/v1/analyze` и `/api/v1/jobs/{job_id}` требуют заголовок `X-API-Key`.
Без ключа или с неверным ключом — `401 {"detail": "Invalid or missing API key"}`; тело запроса при этом не читается.

**Загрузка видео** (пример из ТЗ):

```bash
curl -X POST https://team.example.kz/api/v1/analyze \
     -H "X-API-Key: <ключ>" -F "file=@video_017.mov"
```

Ответ `200`: `{"job_id": "16afab6eee57"}`.

**Статус и результат:**

```bash
curl https://team.example.kz/api/v1/jobs/16afab6eee57 -H "X-API-Key: <ключ>"
```

```json
{
  "job_id": "16afab6eee57",
  "status": "done",
  "verdict": "violation",
  "violations": [
    {
      "type": "Ценности оставлены без присмотра",
      "timecode_sec": 15.2,
      "description": "Кассир покидает кассовое помещение (15.2 с), на рабочем столе остаются наличные или сумка с ценностями. Возможное нарушение требования: Правила осуществления кассовых операций … (постановление Правления НБРК от 29.11.2019 № 231), п. 20 ч. 2 …",
      "evidence_frames": [
        {"timestamp_sec": 15.2, "image_base64": "/9j/4AAQ..."},
        {"timestamp_sec": 20.8, "image_base64": "/9j/4AAQ..."}
      ]
    }
  ]
}
```

- `status`: `processing` (в очереди или в работе), `done`, `failed`. Пока `processing`, `verdict` = `null`, `violations` = `[]`.
  При `failed` добавляется поле `error` с причиной.
- `verdict`: `violation` или `no_violation`; `violations` пустой, если нарушений нет.
- `type` — название типа нарушения из реестра (`cashguard/registry.py`), `description` — что видно на видео
  и норма, которой это может не соответствовать.
- `evidence_frames` — 1–3 JPEG в base64 (без префикса `data:`), на кадре рамки: стол (с вероятностью «деньги на столе», если её запрашивали правила), дверь и экран ноутбука (с ответом VLM, если её спрашивали), сейф (с вероятностью «открыт» / «закрыт»), люди (кассир / посетитель), предметы на столе.

Прочие коды: `404` — неизвестный `job_id`; `400` — пустой файл; `413` — файл больше `CASHGUARD_MAX_UPLOAD_MB`;
`422` — нет поля `file`. Нечитаемое видео принимается, но задача завершается `failed`.

`GET /api/v1/health` (без ключа) — состояние воркера и длина очереди.

## 4. Веб-интерфейс

`http://<хост>:8000/`, без авторизации. Загрузка видео (перетаскиванием или выбором файла) → этапы
«Загрузка → Очередь → Анализ → Результат» с таймером → итог «Нарушение не обнаружено» / «Обнаружены признаки
возможных нарушений». Для каждого нарушения: тип, таймкод, что видно на видео, норма (пункт НПА, дословная цитата
и ссылка на абзац в ИПС «Әділет»), кадры-доказательства (по клику — увеличение). Под видео — метки нарушений
и дорожки фактов, на которых построен вывод: число людей в помещении, сейф открыт, деньги или сумка на столе,
входы и уходы; клик по метке, отрезку, таймкоду или кадру переводит видео к моменту. Внизу — ответ в формате API.
Список последних проверок хранится в браузере; в шапке — состояние сервиса (`/api/v1/health`).

Оформление — в фирменных цветах ForteBank (бордовый и малиновый, шрифт Open Sans) с подписью «Решение кейса
ForteBank · Datathon 26»; логотип банка не используется. Шрифт лежит в `service/static/fonts/`, страница
не обращается к внешним ресурсам.

Интерфейс видит только задачи, загруженные через интерфейс: результаты и видео, отправленные через API жюри,
через страницу не открываются.

## 5. Очередь, хранение, перезапуск

- Один воркер-процесс, задачи по порядку поступления. Статус задачи — в памяти и в `data/service/jobs/<job_id>.json`.
- После перезапуска сервиса незавершённые задачи снова встают в очередь (не больше двух попыток на задачу).
- Если воркер падает, диспетчер поднимает его заново; задача, на которой он упал, повторяется один раз.
- Видео: `data/service/uploads/`. Загруженные через API удаляются после обработки (ТЗ запрещает
  использовать тестовые видео), загруженные через интерфейс остаются для просмотра.
- Кэш признаков `data/cache/<job_id>.json` остаётся: по нему правила можно пересчитать без моделей.
- Лог: `data/service/service.log` и stdout. Для каждой задачи пишется ожидание в очереди, время обработки
  и время от загрузки до результата; превышение 5 минут — `WARNING`.

## 6. Время обработки

Лимит ТЗ — 5 минут от загрузки до результата. Почти всё время уходит на детекторы; правила и кадры — доли секунды.

- Свободный GPU (Apple M4 Max, MPS): 0,7–0,8 × длительности видео (через API: X-38, 59 с → 43 с; X-19, 57 с → 41 с),
  ролик 145 с — около 2 минут. Классификаторы сейфа и денег добавляют по 0,3–1,2 с, VLM — 0–3,2 с.
- GPU занят параллельным обучением (так шёл замер ниже): 1,6–2,7 × длительности. Ролик 145 с в таком режиме
  не уложится в 5 минут и будет снят по `CASHGUARD_JOB_TIMEOUT`. **На время проверки жюри GPU должен быть свободен.**
- Очередь общая: при одновременной отправке нескольких видео каждое следующее ждёт предыдущие,
  а лимит ТЗ считается от загрузки.
